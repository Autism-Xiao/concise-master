# 底座复用与同步约定

本仓库（`concise-master`）是**单仓底座**：`admin-web/`（前端）+ `server/`（后端）在同一 Git 仓库，提供鉴权、RBAC、多租户、数据库双方言、通用组件与工具。新项目从本仓 fork，底座升级后通过 Git `upstream` 一次 merge 同步前后端。**本文随底座一起分发到每个新项目。**

## 一、角色与拓扑

| 角色 | 说明 | 远程 |
| --- | --- | --- |
| 底座 upstream | `concise-master` 单仓，只放通用能力 | `origin` 指向底座仓库 |
| 派生项目 origin | 每个新项目独立仓库（内含前后端两目录） | `origin` 指向自己的仓库，`upstream` 指向底座 |

前后端在**同一条同步线**上：一次 `fetch upstream && merge upstream/main` 同时更新 `admin-web/` 和 `server/`。一个项目 = 一个仓库（含前后端两个目录）。

## 二、分层边界（最重要）

同步是否轻松，取决于是否守住这条边界：**底座层只跟随 upstream 更新，业务层才是你写自己代码的地方。**

### 后端 `server/`

- **底座层（不要直接改）**：`server/src/shared/`、`server/src/common/`、`server/src/config/`、`server/src/constants/`、`server/src/global/`、`server/src/helper/`、`server/src/utils/`、`server/src/migrations/`、`server/src/main.ts`、`server/src/app.module.ts`、`server/package.json`、`server/tsconfig*`、`server/nest-cli.json`、`server/Dockerfile`、`server/docker-compose.yml`、`server/deploy/`、`server/scripts/`
- **业务层（放心写）**：`server/src/modules/<你的业务>/`，例如 `server/src/modules/biz_order/`、`server/src/modules/supplier/`

### 前端 `admin-web/`

- **底座层（不要直接改）**：`admin-web/src/components/`、`admin-web/src/hooks/`、`admin-web/src/lib/`、`admin-web/src/stores/`、`admin-web/src/config/`、`admin-web/src/context/`、`admin-web/src/routes/`、`admin-web/src/assets/`、`admin-web/src/index.css`、`admin-web/src/main.tsx`、`admin-web/package.json`、`admin-web/vite.config.ts`、`admin-web/tsconfig*`、`admin-web/index.html`
- **业务层（放心写）**：`admin-web/src/features/<你的业务>/`，例如 `admin-web/src/features/biz_order/`

### 需要改底座行为怎么办

不要直接编辑底座文件。优先用这些方式：

1. 配置覆盖：环境变量、`src/config/` 里已有开关、数据库系统参数。
2. 扩展点：在业务模块里实现底座已定义的接口/钩子，通过模块注册注入。
3. 反向贡献：如果改动是通用的，在底座仓库提 PR，合并后所有项目一起同步（这是唯一正确的"改底座"路径）。

## 三、初始化新项目（每个项目一次）

```bash
git clone https://github.com/Autism-Xiao/concise-master.git my-blog
cd my-blog

# 用随底座分发的脚本，在项目根跑一次，完成 upstream 配置
bash server/scripts/sync-base.sh --init
# 脚本会把原 origin（底座）改名为 upstream，并提示你添加自己的 origin

git remote add origin https://github.com/你/my-blog.git
git push -u origin main
```

完成后项目仓库应有两个远程：`origin`（自己）、`upstream`（底座）。前端 `admin-web/` 与后端 `server/` 都在这一个仓库里。

## 四、日常同步

在**项目根目录**执行，一次同步前后端：

```bash
# 先看落后多少提交，不改动任何文件
bash server/scripts/sync-base.sh --check

# 实际同步：fetch upstream -> merge -> push origin
bash server/scripts/sync-base.sh

# 只想合并、暂不 push（推荐先用这个观察结果）
bash server/scripts/sync-base.sh --no-push
```

脚本行为：

- 工作区有未提交改动时**拒绝同步**，避免把你的草稿卷进合并。
- 合并冲突时列出冲突文件，并按"底座层/业务层"分类。
- 业务层出现冲突 = 你违反分层约定改过底座文件，应把改动提回底座。
- 底座层冲突属正常现象，手工解一下即可。

## 五、冲突处理

```bash
git status                      # 看哪些文件冲突
git add <已解决的文件>
git commit --no-edit            # 完成合并
git push origin main
# 或者放弃本次同步
git merge --abort
```

解冲突时，**保留底座的实现，把你的定制迁移到业务层**，而不是简单二选一。

## 六、数据库迁移注意

底座 migration 与业务 migration 共存于 `src/migrations/{mysql,postgres}/`，版本号是时间戳，跨仓库同步时可能撞号。约定：

- 底座迁移时间戳用现有号段（如 `1794xxxxxxxx`、`17942xxxxxxxx`）。
- 业务迁移时间戳往**更大**的号段取（如以 `19` 开头的 13 位时间戳），避免与底座冲突。
- 新增迁移后，MySQL 与 PostgreSQL 两个目录都要生成，保持双方言一致。
- 生产环境执行迁移前先备份（参考 `scripts/dump-sql.mjs`）。

## 七、密钥与本地配置

`.env`、`*.local`、密钥、数据库口令**永不入库**。新项目 clone 后按 `.env.example` 自行生成。底座升级若新增配置项，同步后对照 `.env.example` 补齐本地 `.env`。

## 八、什么时候不该用这套

- 项目需要深度改造底座（换数据库、换鉴权体系）：fork 会持续冲突，建议独立仓库 + 定期手工移植，或改用 monorepo 共享包。
- 项目只是临时演示：直接 clone 一份即可，不必配 upstream。
