# 角色基线 + 例外授权配置规范 v1

> 适用范围：Concise Admin 的功能权限（菜单/按钮）与数据权限（可见行）。
> 配套底座：`sys_role`（职能角色）、`sys_grant`（例外授权）、`sys_data_rule`（行级规则）。
> 本规范回答一个问题：**一个新权限需求，应该建角色，还是挂个人授权？**

---

## 一、四条铁律

1. **角色是职能基线，授权是例外增量。** 角色回答"这个岗位平时干什么"，授权回答"这个人这次多干什么"。
2. **加用授权，减用角色。** `最终权限 = 角色权限 ∪ 个人授权（去重）`，并集只能加不能减。要少给权限，换更窄的角色，不要用授权去"抵消"。
3. **菜单归授权，数据归规则。** 能不能进页面/点按钮 = 权限码（`sys_grant.permission_id`）；能看到哪些行 = 数据规则（`sys_grant.rule_id` → `sys_data_rule`）。两者独立配置。
4. **临时必填过期，长期必填理由。** 授权不填 `expire_at` 或 `reason` 的不予创建，避免半年后没人知道为什么有这个权限。

---

## 二、判定标准（五问，按顺序问）

| 顺序 | 问题 | 是 → | 否 → |
|---|---|---|---|
| 1 | 是岗位职责的一部分吗？ | 建/用**角色** | 下一问 |
| 2 | 有 ≥3 人长期需要（>3 个月）吗？ | 建**角色**，或挂**岗位/部门授权** | 下一问 |
| 3 | 是 ≤3 个月、一次性、跨部门吗？ | 挂**个人授权** + `expire_at` | 下一问 |
| 4 | 是想"少给"某个权限吗？ | **换更窄角色**（授权做不到） | 下一问 |
| 5 | 是想控制"看哪些行"吗？ | 配**数据规则**，不是菜单授权 | 不需要授权 |

两条硬边界（在 `PermsGuard` 里前置拦截，配了也不生效）：

- **平台级权限**（`sys_permission.scope = 'platform'`，如 `system:tenant:*`、`system:menu:*`、代码生成）只有平台管理员可用，个人授权无效。
- **租户套餐是硬上限**：`最终权限 = (角色 ∪ 授权) ∩ 套餐`，个人授权不能突破租户未开通的模块。

---

## 三、四类主体各管什么

`sys_grant.subject_type` 支持 `user / dept / position / role` 四类：

| 主体 | 用途 | 典型场景 | 建议过期 |
|---|---|---|---|
| `role` | 给已有角色补权限，不改菜单树、不影响其他角色 | 财务角色额外需要"导出" | 长期可不填 |
| `position` | 岗位级共性，且岗位由 HR 统一维护 | 所有"订单专员"都能看订单 | 长期可不填 |
| `dept` | 组织级整体授权，避免为一个部门新建角色 | 市场部全员临时看供应商 | 建议填 |
| `user` | 个别人的例外 | 小张临时看订单/供应商 | **必填** |

**防双重控制**：同一权限点不要既在角色里配、又在岗位/部门里配。人员调动后来源说不清。每个权限点只有一个"职能来源"，个人授权是叠加层。

---

## 四、建议的最小角色基线

针对客户 / 订单 / 供应商三个业务模块，角色控制在 5 个以内：

| 角色编码建议 | 权限范围 | 说明 |
|---|---|---|
| `base_employee` | 仅首页、个人资料 | **所有账号必挂**，见下方 P0 |
| `role_customer` | 客户管理增删改查 | 客户岗 |
| `role_order` | 订单管理增删改查 | 订单岗 |
| `role_supplier` | 供应商管理增删改查 | 供应商岗 |
| `role_tenant_admin` | 租户内系统管理 | 不含平台级权限 |

> **P0 提醒**：当前 `PermsGuard` 对**无角色用户直接拒绝**（`roles.length === 0 → 无操作权限`），即使挂了个人授权也不放行。所以"只有个人授权、没有角色"的账号现在跑不通——`base_employee` 这个空壳基线角色是必需的，不是可选项。要支持纯个人授权账号，需改守卫放行逻辑。

## 五、三个账号的配置示例

| 账号 | 目标 | 配置 | 备注 |
|---|---|---|---|
| `xiaozhang` | 看客户，额外看订单/供应商 | `base_employee` + `role_customer` + 两条个人授权（`biz_order:list`、`supplier:list`，只读） | 授权填理由；若只看自己建的，再绑 `self` 规则 |
| `wangorder` | 看订单 | `base_employee` + `role_order` | 无个人授权 |
| `xiaoli` | 看供应商（原先错挂订单） | `base_employee` + `role_supplier` | **先解绑订单角色**，不要用授权去"抵消"订单权限 |

## 六、授权与规则填写规范

### 授权行（`sys_grant`）

- `reason` 模板：`[场景] 谁申请 / 谁审批 / 事由`，例：`[跨部门协作] 小张查看订单，仅本周核对用`。
- `expire_at`：临时授权必填；确需长期，理由里写明"长期"并按季度复核。
- `rule_id`：只在需要限制可见行时绑，且按动作配（`read` 全部、`write` 仅本人、`delete` 不配即不允许）。
- 同一主体 + 同一权限点只允许一条有效授权，重复会报错，直接改原记录。

### 数据规则（`sys_data_rule`）

- `action`：`all`（读写通用，存量默认）/ `read` / `write` / `delete`。**精确 action 规则优先于 `all`**，所以"看全部、只改自己"要配两条：`read` 全量 + `write` self。
- `rule_field`：必须是实体属性名（白名单），写错会被翻译层挡掉并按"无可见数据"处理。
- `rule_operator`：`eq/ne/gt/gte/lt/lte/in/not_in/like/self/dept`；`self` / `dept` 落到归属列（默认 `create_by`）。
- `rule_value`：可用上下文变量 `$user.id`、`$user.deptIds`；`in/not_in` 用逗号分隔。
- `rule_effect`：allow 之间是 OR，deny 之间是 AND NOT，deny 优先级高于 allow。
- `priority`：数值小的先应用。
- 规则被授权引用时不允许删除，先解绑再删。

## 七、反例清单

1. **一人一角色** → 角色爆炸，回到老问题。
2. **想用个人授权收回角色的删除按钮** → 做不到，换角色。
3. **给角色配一条 `all` 的"看全部"规则图省事** → 写/删动作也跟着放大；应按 action 拆规则。
4. **授权不填过期和理由** → 半年后没人知道为什么有这个权限。
5. **同一权限既挂角色又挂岗位** → 人员调整后来源不清。
6. **把 `menuType=2` 的按钮节点当成菜单授权** → 只出按钮不出菜单，页面进不去；菜单节点和按钮节点要分别授权。
7. **给无角色账号挂个人授权** → 当前守卫直接拒绝，必须先挂 `base_employee`。

---

## 八、落地顺序

1. 建 5 个基线角色，先建 `base_employee` 并全员挂上；
2. 按职能给三个账号挂角色，纠正 `xiaoli` 的角色错配；
3. 用个人授权补 `xiaozhang` 的订单/供应商只读；
4. 需要控行时再配数据规则，绑到对应授权；
5. 用「授权管理」「数据规则」两个页面维护第 3、4 步（此前只能调 API）。

---

## 九、配置页与接口对照

| 页面 | 路由 | 后端接口 | 权限码 |
|---|---|---|---|
| 授权管理 | `/system/grant` | `/api/v1/grants` | `system:grant:list` / `system:grant:write` |
| 数据规则 | `/system/data-rule` | `/api/v1/data-rules` | `system:rule:list` / `system:rule:write` |

两个页面的菜单节点由迁移写入 `sys_permission`，`url` 必须与前端路由完全一致，否则侧边栏不显示、路由守卫也会拦。
